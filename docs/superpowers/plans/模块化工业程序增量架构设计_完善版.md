# 模块化工业程序增量架构设计（完善版）

> 适用场景：工业产量表单采集、识别、审核、追溯、导出与后续 React / Tauri 产品化  
> 架构策略：增量改造、模块化单体、单机可运行、服务器可迁移、AI 可插拔  
> 当前阶段：保留现有领域逻辑与 SQLite 单机闭环，新增 FastAPI 接口层与后续前端边界

---

## 1. 目标与约束

本次优化的目标，是在**不改写现有业务闭环**的前提下，为以下能力补齐稳定的基础架构：

- 多人协作开发；
- React 前端；
- Web / Tauri 双运行外壳；
- FastAPI 接口层；
- 多人审核与并发控制；
- 后台任务与进度推送；
- 服务器部署；
- 工业设备接入；
- 数据迁移、备份与恢复；
- 可观测性和错误追踪；
- AI、向量检索和音频转写的可选接入。

现有能力继续保留并复用：

- 领域实体；
- 应用服务；
- SQLite；
- 本地证据目录；
- 图像识别；
- 规则校验；
- 审计；
- 查询；
- 数据血缘；
- XLSX 导出；
- 可选 AI Adapter；
- 本地相似检索；
- Streamlit 工程原型。

当前仓库尚无正式 FastAPI 实现，本次新增 FastAPI 接口层，但不得将其演变为对现有后端业务的整体重写。

系统继续采用**模块化单体**，不提前拆分微服务。模块之间通过 Application Port、公开用例和领域事件协作，不直接依赖其他模块的数据库 Adapter。

---

## 2. 核心架构原则

1. **增量式改造**：先建立边界，再逐步内聚，不一次性迁移全部旧代码。
2. **模块化单体**：当前阶段不拆微服务。
3. **数据库是事实源**：业务事实由结构化数据库保存。
4. **证据文件是证据源**：原图、裁切图和录音只读保存。
5. **AI 只做建议**：OCR、OMR、ASR、向量检索和大模型不得直接替代人工确认。
6. **正式值唯一**：人工确认后的当前有效版本才是正式业务值。
7. **所有变更留痕**：正式修改必须产生版本和审计记录。
8. **导出可追溯**：任一 XLSX 数据都必须能追溯到明确表单版本、字段版本和原始证据。
9. **前后端解耦**：前端不得直接访问数据库、文件绝对路径或设备 SDK。
10. **基础设施可替换**：SQLite、本地文件、进程内任务和本地索引均需通过 Port 隔离。
11. **短事务原则**：OCR、图片处理、文件生成期间不得长期持有数据库事务。
12. **可选模块可降级**：AI、向量和音频转写关闭时，核心业务必须继续运行。
13. **不静默覆盖**：多人修改必须使用审核 Lease 与乐观锁。
14. **不隐藏错误**：API、任务和日志均需使用稳定错误码与 request_id。
15. **不破坏现有数据**：任何迁移、恢复和修复流程都必须可验证、可回滚。

## 5. Application Facade、Port 与 Adapter

### 5.1 分层规则

- Domain 不导入 FastAPI、SQLAlchemy、Streamlit、React、Tauri 或设备 SDK。
- Application 定义用例、事务边界和 Port。
- Adapter 实现数据库、文件、任务、向量、通知和设备能力。
- API 和 UI 只调用 Application Facade。
- 模块不得直接调用其他模块的数据库 Adapter。
- 模块协作通过公开用例、Application Port 或领域事件。

## 6. Unit of Work 与事务边界

以下操作必须原子完成：

- 表单确认；
- 字段更正；
- 退回；
- 作废；
- 当前版本切换；
- RecordVersion 增加；
- AuditEvent 写入；
- 导出批次创建；
- 导出明细快照；
- 审核锁校验；
- 任务终态写入。

要求：

- Application Command 通过 `UnitOfWork` 执行；
- Repository 不得内部任意 `commit()`；
- 一个业务命令原则上只提交一次；
- 业务数据、版本和审计同时成功或同时回滚；
- 事务失败时不得发布成功事件；
- 领域事件在事务提交后发布；
- OCR、图像处理和文件生成不得占用数据库长事务；
- 文件应先写临时位置、校验哈希，再原子移动；
- 外部文件失败时不得留下指向不存在文件的正式记录。

## 8. 幂等控制

以下操作支持 `Idempotency-Key`：

- 图片导入；
- 批量识别；
- 重识别；
- 确认；
- 更正；
- 导出；
- 音频转写；
- 向量生成。

规则：

- 同 actor、同操作、同资源、同 key、同请求体：返回首次结果；
- 相同 key 但请求体不同：返回 409；
- 不同操作使用不同作用域；
- 幂等记录设置保留期；
- 导出幂等必须防止重复批次。

## 10. 多人审核锁与乐观并发

### 10.1 ReviewLease

字段：

```text
form_id
owner_id
lease_token
acquired_at
expires_at
heartbeat_at
forced_release_by
forced_release_reason
```

规则：

- 同一表单同时只有一个有效 Lease；
- 其他用户只读；
- Lease 必须过期；
- Web / Desktop 定时 heartbeat；
- 页面异常关闭后自动过期；
- 管理员可带原因强制释放；
- 获取、续租、释放、强制释放均记录审计；
- 过期 Lease 不得继续确认。

### 10.2 乐观锁

核心实体增加：

```text
version
updated_at
```

写请求统一使用：

```text
expected_version
```

版本冲突返回 409，并返回：

- submitted_version；
- current_version；
- request_id；
- 重新加载提示。

确认时同时验证：

- 权限；
- lease_token；
- Lease owner；
- Lease 有效期；
- expected_version；
- 当前状态；
- 规则结果。

- 不提供普通修改接口；
- 不允许业务操作删除审计事件；


不得记录密码、Token、完整敏感录音、二进制内容或不必要隐私。

### 15.2 Request ID

- 接收或生成 `X-Request-ID`；
- 响应头返回同一 ID；
- 错误响应包含 request_id；
- 任务、审计和日志继承 request_id。

### 15.3 健康检查

```text
GET /health/live
GET /health/ready
```

`live`：仅表示进程存活。

`ready` 检查：

- 数据库；
- Alembic 版本；
- 证据目录；
- 必要配置；
- 任务执行器；
- 核心 Adapter。

AI、向量或音频转写不可用时，不应导致核心服务不可用，但应返回 capability 降级状态。

### 15.4 ErrorTracker

定义 `ErrorTrackerPort`，默认本地日志实现，服务器阶段可替换为 Sentry 或 OpenTelemetry。

## 16. SQLite 运行约束

单机阶段：

- WAL；
- `foreign_keys=ON`；
- `busy_timeout`；
- 短事务；
- 有限任务并发；
- 统一连接管理；
- OCR 期间不持有事务；
- 避免长时间写锁。

需要迁移 PostgreSQL 的信号：

- 多终端同时写入；
- 锁冲突持续出现；
- Worker 独立部署；
- 审计和任务事件量大幅增加；
- 需要高可用；
- 需要集中服务器；
- 需要复杂并发查询。

## 17. Alembic 迁移

要求：

- 建立基线；
- 正式数据库不依赖 `create_all` 升级；
- 结构变化必须有迁移；
- 空库可完整升级；
- 已有库可基线接入；
- 尽量兼容 SQLite 和 PostgreSQL；
- 新增任务、Lease、版本、幂等和导出快照必须有迁移；
- 迁移前建议备份；
- 迁移失败不得破坏当前数据；
- 文档说明升级和回滚。

## 19. 一致性检查

命令：

```bash
python -m app.tools.verify_integrity
```

检查：

- 外键；
- 缺失证据；
- 孤立文件；
- SHA-256 不一致；
- 孤立裁切图；
- 当前版本指针缺失；
- 导出引用无效版本；
- 导出文件缺失；
- 长期未释放 Lease；
- 无执行器的 RUNNING 任务；
- 重复有效导出；
- 模板版本缺失；
- 审计引用不存在对象。

要求：

- 默认只生成报告；
- 不自动修复；
- 输出 JSON 和人类可读摘要；
- 支持非零退出码。
