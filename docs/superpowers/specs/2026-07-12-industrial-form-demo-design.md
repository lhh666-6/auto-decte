# 工业级产量数据采集 Demo 设计

## 1. 目标与范围

本项目在单台 Windows 10/11 电脑上实现工业产量表单采集 Demo。系统必须优先打通无 OCR、无 AI 时的人工闭环，再逐步加入图像识别、规则审查和可选 AI 能力。

首个可运行闭环为：导入图片、创建表单、人工选择模板、人工录入或复核、规则校验、确认新版本、精确查询与追溯、导出 XLSX。原始证据、识别候选、AI 建议、人工确认值和历史版本分别保存，禁止相互覆盖。

项目严格遵守根目录《工业级产量数据采集_Demo开发文档_AI协作版.md》的 Demo 边界，不在本轮实现多车间高并发、生产级服务器、正式工资系统直连或 AI 自动审批工资数据。

## 2. 技术架构

- Python 3.11 作为运行环境。
- Streamlit 提供本地 Web UI。
- SQLite 与 SQLAlchemy 保存表单事实、当前版本、历史版本、识别尝试、审计事件和导出批次。
- 本地分层证据目录保存原图、校正图、字段裁切图和录音；数据库只保存文件 ID、URI、SHA-256 和元数据。
- OpenCV 负责图像质量检测、旋转、透视校正、二维码读取和字段裁切。
- OCR、OMR、AI 和向量检索均通过 Adapter 接口接入，可以关闭或替换。
- openpyxl 生成工资、产量和质量 XLSX，并写入可反向定位 ExportBatch、RecordVersion、FormField 和证据的标识。
- pytest 覆盖领域规则、存储适配器和端到端关键路径。

核心依赖方向为 UI → Application Services → Domain。数据库、文件、OCR、AI、向量库和 XLSX 均为外部 Adapter，领域层不得依赖 Streamlit、OpenCV 或具体数据库实现。

## 3. 核心组件

### 3.1 领域与状态

领域层定义 Form、FormField、RecognitionAttempt、EvidenceFile、RecordVersion、AuditEvent 和 ExportBatch。复核状态与导出状态分开管理。`current_value` 只允许来自最新人工确认值或明确批准的自动通过值。

### 3.2 导入与证据存储

导入服务计算 SHA-256，检测重复文件与重复表单，并将原始证据写入不可静默覆盖的位置。重新采集必须生成新的证据记录。录音只有满足 E99、自由说明、非常规更正或争议条件时才允许绑定。

### 3.3 人工复核与版本

复核页面同屏显示原图、字段裁切、OCR 候选与置信度、规则结果、可选 AI 建议、录音、历史版本和导出影响。确认或更正创建新的 RecordVersion 和 AuditEvent，不修改历史记录。

### 3.4 图像与识别

图像管线依次执行质量检测、旋转或透视校正、模板定位和字段裁切。二维码优先确定模板；低置信度结果进入人工分类。OCR/OMR 只创建 RecognitionAttempt，绝不直接覆盖当前有效值。

### 3.5 规则、查询与导出

规则引擎执行必填、范围、数量闭合、主数据有效性、重复表单、当前版本、导出完整性等确定性校验，并返回字段级机器可读错误码。精确统计只查询 SQLite。XLSX 只导出当前有效且允许导出的版本；已导出记录发生更正后标记为 `REEXPORT_REQUIRED`。

### 3.6 可选 AI 与向量检索

AI 仅输出带证据的异常摘要和建议，不写入业务事实。向量检索只用于相似异常、录音和备注检索，不用于工资统计或当前版本判断。AI 或向量服务不可用时，导入、复核、规则、查询、追溯和 XLSX 导出继续工作。

## 4. 数据流与错误处理

导入文件后先生成证据记录和表单，再执行分类、图像处理、识别和规则校验。任何自动步骤失败都记录明确错误码和审计事件，并将表单送入人工队列；失败不得破坏已保存证据或阻断其他表单处理。

图像质量不合格时进入 `RECAPTURE_REQUIRED`。模板不确定时进入 `NEEDS_CLASSIFICATION`。识别或规则存在风险时进入 `NEEDS_REVIEW`。只有 `CONFIRMED` 或经批准的 `AUTO_APPROVED` 版本可导出。

## 5. 两人协作与 GitHub 流程

采用混合接力模式。开发者 A 先完成基础架构和人工闭环；开发者 B 加入后负责图像识别专项；最终由两人交叉审查和联调。

- `main` 始终保持可启动、可测试。
- 每个阶段使用 `phase-N-description` 分支和独立 Pull Request。
- PR 合并后，下一阶段从最新 `main` 创建分支。
- 第二位开发者加入前，开发者 A 可以合并自己的 PR，但保留 PR、测试和进度记录。
- 第二位加入后，每个 PR 由另一位开发者或另一 Codex 会话审查。
- 每次接力前执行 `git pull --ff-only`。

## 6. 阶段与负责人

| 阶段 | 负责人 | 交付物 | 退出条件 |
|---|---|---|---|
| P0 项目初始化 | A | 工程骨架、配置、数据库、测试框架 | 应用可启动，测试可运行 |
| P1 人工闭环 | A | 导入、证据存储、模板选择、人工复核 | 无 OCR 可完成单张表单确认 |
| P2 查询与导出 | A | 精确查询、追溯、XLSX | XLSX 数据可反查原图和版本 |
| P3 图像与识别 | B | 校正、二维码、OCR、OMR | 候选进入复核且不覆盖人工值 |
| P4 规则与审计 | A 主导、B 审查 | 规则、异常队列、重复检测 | 修改和确认均有审计事件 |
| P5 AI 与向量 | B 主导、A 审查 | 可关闭 AI、摘要、相似检索 | AI 关闭时核心流程正常 |
| P6 联调验收 | 共同 | 集成、性能和试点报告 | 达到源需求文档的 Demo 指标 |

开发者 A 在开发者 B 加入前完成 P0、P1、P2，并建立 P4 所需的领域接口；开发者 B 从 P3 开始接力。

## 7. 明文进度机制

仓库根目录使用 `PROGRESS.md` 作为唯一接力状态文件。每个阶段必须记录状态、负责人、分支、起止时间、已完成、未完成、验证命令、验证结果、最新提交、已知问题和下一位操作。

功能代码、测试和进度更新必须出现在同一个 PR。阶段状态不得只写“已完成”，必须给出实际验证命令与结果。阻塞事项必须写入 `PROGRESS.md`，不能只保留在 Codex 对话中。

## 8. 测试与验收

- 领域规则使用单元测试覆盖正常、边界和拒绝路径。
- 数据库、证据存储和导出使用集成测试验证不可覆盖、版本关系和文件哈希。
- 人工闭环必须在 OCR、AI 和向量检索全部关闭时通过端到端测试。
- OCR/OMR 使用独立金标准数据集评估，不允许用最终测试集调参。
- 每个阶段合并前运行该阶段测试；P6 运行全量测试和源需求文档中的必测场景。
- 任一导出值必须能够追溯到导出批次、表单、字段、当前版本、识别尝试、原始证据和审计事件。

## 9. 安全约束

表单、工资数据和录音默认不上传公共云。外部 AI 只有在取得授权并完成脱敏后才能启用。原始证据只读；所有更正、确认、作废、导出和重算均生成 AuditEvent。任何秘密和真实业务数据不得提交到 GitHub。
